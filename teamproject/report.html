Memory Match

Web Programming Team Project Report

Memory Match · Sudip, Sondor, Eric and Abinash

Memory Match is an interactive browser game that demonstrates DOM events, state management, responsive styling, and testable JavaScript rules.

Report updated: 31 October 2026

Abstract

Memory Match is a static browser application in which players reveal cards and identify matching symbols. It supports timed play, practice and a local two-player duel. The implementation separates JavaScript game rules from DOM interaction and provides configurable difficulty, preview, hints and combo scoring. Six existing automated engine tests passed in the recorded test run on 26 October 2026. The project demonstrates event handling and explicit state management; it does not evaluate changes in human memory performance.

1. Objective

The project turns a matching-card activity into a complete browser interaction. Players reveal pairs of symbols while the application tracks selections, progress, moves, points, and remaining resources. The learning objective is to connect HTML controls and CSS states with predictable JavaScript behavior.

2. Features and scope

Players choose timed, practice, or local duel mode. Timed mode ends at zero seconds; practice and duel have no countdown. A correct duel match keeps the turn, while a mismatch passes it. The player with the most pairs wins the duel.

4. Data and algorithm

The state includes cards, open indexes, matched pairs, moves, streak, points, hints, time, phase, current player, and the two players' pair counts. Each card stores a symbol and a matched flag. Card creation duplicates each selected symbol and shuffles the resulting array with Fisher–Yates.

The flip function accepts selections only during playing. A first selection stores one index. The second selection counts as a move and compares symbols. A match marks both cards and updates progress. A mismatch locks the game briefly. After 800 ms, settle clears the open indexes, changes the duel player if necessary, and returns to playing.

5. Scoring and timing

The reward is 100 + min(streak - 1, 4) × 25 after increasing the streak. Rewards are 100, 125, 150, 175, and then 200 for later consecutive matches. A miss resets the streak. Hint use deducts 50 points with a minimum total of zero.

The interface checks elapsed time using performance.now. It updates the countdown through an interval and when tab visibility changes. The preview has a separate deadline. The timer does not run during preview. Restart clears both interval and reveal timeout before rebuilding the board.

6. State transitions

A round moves from preview to playing. A mismatch temporarily changes playing to mismatch; settle returns it to playing. Hint use temporarily changes playing to hint. Finding the final pair produces won. An expired timed round produces lost. The engine rejects card flips outside playing, and settle cannot revive a lost round.

9. Limitations and improvements

The round state disappears on reload. Duel requires both players to share a device. Future development could add local saved scores, optional sounds, and a clearer turn summary. Network multiplayer would require additional architecture and is outside this version.

10. Running the application

Open the deployed game, or extract the repository and serve its root directory with python -m http.server 8000. Then visit http://localhost:8000/teamproject/. A local HTTP server supports the JavaScript module imports. Node is needed to run the automated engine tests, but the deployed game runs in the browser without a build step.

12. Conclusion

The application connects HTML structure, CSS feedback and JavaScript event handling through a defined game state. Separating the engine from the interface supports focused rule testing and makes matching, scoring and timing behavior easier to explain. The current implementation supports local gameplay and the documented controls. Persistent scores and network multiplayer remain outside its present scope.
